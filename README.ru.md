# Adaptive Code Memory

> **Гетерогенная память с адаптивным распределением информационного бюджета для рассуждений о кодовых репозиториях**

**Статус:** Исследование / Ранняя разработка  
**Категория:** AI / Machine Learning / Code Intelligence / Representation Learning  
**Фокус:** Латентные представления, гетерогенная память, информационные ограничения, адаптивное сжатие, рассуждения о коде, LLM

---

# Обзор

Современные языковые модели способны удивительно хорошо рассуждать об исходном коде, однако большие репозитории создают фундаментальное ограничение по объёму доступной информации.

Репозиторий может содержать десятки или сотни тысяч токенов:

```text
Репозиторий
├── исходный код
├── модули
├── классы
├── функции
├── зависимости
├── конфигурация
└── документация
```

Традиционные системы решают эту проблему с помощью больших контекстных окон, retrieval-augmented generation, поиска по коду, графовых методов извлечения информации или сжатия контекста.

Другое направление исследований пытается сжать информацию о репозитории в компактные латентные представления.

Этот проект исследует другую гипотезу:

> **Знания о репозитории неоднородны, поэтому может быть принципиально неэффективно сжимать всю информацию в одно представление.**

Код содержит принципиально разные типы информации:

```text
Семантическая
«Что делает этот компонент?»

Структурная
«Как эти компоненты связаны между собой?»

Символическая
«Как называется эта функция?»

Поведенческая
«Что произойдёт при таком условии?»

Литеральная
«Каково точное значение этой константы?»
```

Эти типы информации обладают разными свойствами и могут требовать разных представлений.

Вместо того чтобы пропускать всё через один механизм сжатия, проект исследует **гетерогенную память кода**, состоящую из нескольких взаимодополняющих представлений.

Концептуально:

```text
                         Репозиторий
                              │
                              ▼
                     Анализ кода
                              │
               ┌──────────────┼──────────────┐
               │              │              │
               ▼              ▼              ▼
          Семантическая   Структурная    Символическая
             память         память          память
               │              │              │
               ▼              ▼              ▼
           Латенты          Граф         Точные факты
               │              │              │
               └──────────────┼──────────────┘
                              │
                              ▼
                    Адаптивный маршрутизатор
                              │
                              ▼
                   Информационный бюджет
                              │
                              ▼
                         LLM-получатель
                              │
                              ▼
                            Ответ
```

Центральная идея заключается не просто в том, чтобы сильнее сжимать информацию.

Цель — исследовать, действительно ли **разные типы знаний о репозитории следует по-разному представлять, хранить и передавать при ограниченном информационном бюджете**.

---

# Исследовательский вопрос

Главный исследовательский вопрос:

> **Может ли гетерогенная семантическая, структурная и символическая память сохранять больше информации, необходимой для выполнения задач над репозиторием, чем монолитное сжатие при одинаковом информационном бюджете?**

Из него следуют дополнительные вопросы:

- Превосходит ли гетерогенная память единый латентный bottleneck?
- Какие типы знаний о коде лучше всего сохраняются в каких представлениях?
- Можно ли эффективно хранить семантическую информацию в непрерывных латентных представлениях?
- Лучше ли представлять структурную информацию явно в виде графа?
- Лучше ли сохранять точную символическую информацию детерминированно?
- Может ли обучаемый маршрутизатор динамически распределять память в зависимости от вопроса?
- Может ли система использовать больше информации только тогда, когда это действительно необходимо?
- Улучшает ли адаптивное распределение информационную эффективность?
- Переносится ли обученная память между различными моделями-получателями?
- Можно ли с помощью контрфактуальных экспериментов доказать, что ответы действительно зависят от сохранённой памяти?
- Какое количество производительности можно получить на единицу информационного бюджета?

# Мотивация

Большие кодовые базы содержат разные типы информации, которые ведут себя совершенно по-разному при сжатии.

Рассмотрим следующую функцию:

```python
def authenticate_user(token):
    if not verify_signature(token):
        raise AuthenticationError()
    return get_user_from_token(token)
```

Система может получить вопрос:

> Что делает эта функция?

В первую очередь здесь требуется **семантическая информация**.

Но другой вопрос:

> Какую функцию вызывает `authenticate_user()`?

Требует **структурной информации**.

Ещё один:

> Как называется исключение?

Требует **символической информации**.

И:

> Что происходит при неудачной проверке подписи?

Требует **поведенческой информации**.

Единое латентное представление должно неявно кодировать всё это одновременно.

Это возможно, однако не обязательно оптимально.

Поэтому центральная гипотеза проекта:

> **Информационная структура программ неоднородна, и архитектура памяти должна отражать эту неоднородность.**

---

# Основная гипотеза

Основная гипотеза:

> **При фиксированном информационном бюджете адаптивная гетерогенная память, которая распределяет ёмкость между семантическим, структурным и символическим представлениями, будет сохранять больше информации, необходимой для выполнения задач, чем монолитное латентное представление или стратегия равномерного сжатия.**

Гипотезу можно представить так:

```text
                    Фиксированный информационный бюджет
                                      │
             ┌────────────────────────┼────────────────────────┐
             ▼                        ▼                        ▼
        Семантическая             Структурная             Символическая
           память                   память                    память
             │                        │                        │
             └────────────────────────┼────────────────────────┘
                                      ▼
                            Адаптивное распределение
                                      │
                                      ▼
                                 LLM-получатель
```

Система не предполагает, что каждому вопросу требуется одинаковый тип информации.

Например:

```text
Вопрос:
«Как работает аутентификация?»

Семантика       ████████████████████
Структура       █████
Символы          ██
```

А для:

```text
Вопрос:
«Где вызывается validate_token()?»

Семантика       ███
Структура       ████████████████████
Символы         ████
```

И для:

```text
Вопрос:
«Каково точное значение константы timeout?»

Семантика       █
Структура       ██
Символы         █████████████████████
```

Приведённое распределение является иллюстрацией, а не заранее установленным дизайном.

Эксперименты должны определить, действительно ли такая специализация полезна.

---

# Исследовательская позиция

Проект **не предполагает**, что латентная память автоматически лучше retrieval.

Современные исследования уже рассматривают сжатие контекста на уровне репозиториев через различные подходы, включая дискретное сжатие токенов, непрерывные латентные представления и другие методы компактного представления.

Адаптивное сжатие кода и retrieval с учётом структуры репозитория также являются активно развивающимися направлениями.

Поэтому цель проекта не:

> «Мы изобрели сжатие кода».

И не:

> «Латентные представления заменяют RAG».

Вместо этого проект исследует более узкий вопрос:

> **Даёт ли разное представление разных классов знаний о коде преимущество, когда общий информационный бюджет ограничен?**

Это различие является центральным для исследования.

---

# Что такое гетерогенная память кода?

Предлагаемая память состоит из нескольких взаимодополняющих компонентов.

## 1. Семантическая память

Семантическая память пытается сохранять информацию о высокоуровневом смысле.

Возможная информация:

- что делает функция;
- за что отвечает модуль;
- назначение компонента;
- высокоуровневое поведение;
- концептуальные связи;
- намерение реализации.

Возможное представление — обучаемая непрерывная латентная память:

```text
Код
 │
 ▼
Семантический энкодер
 │
 ▼
z₁ z₂ z₃ ... zₖ
```

Представление не обязано напрямую соответствовать текстовым токенам.

---

# 2. Структурная память

Структурная память представляет отношения между компонентами.

Например:

```text
импортирует
вызывает
наследуется от
реализует
ссылается на
зависит от
содержит
```

Концептуально:

```text
A ──вызывает──► B
B ──импортирует─► C
D ──наследуется от──► A
```

Графовое представление может сохранять информацию, которую было бы неоправданно дорого кодировать в непрерывные латентные векторы.

Возможная структура:

```text
Репозиторий
    │
    ▼
AST / статический анализ
    │
    ▼
Граф кода
    │
    ▼
Графовое представление
```

Точная реализация является исследовательской переменной.

---

# 3. Символическая память

Символическая память хранит информацию, где особенно важна точность.

Например:

```text
имена функций
имена классов
количество аргументов
типы
константы
литералы
пути к файлам
импорты
ссылки на строки
```

Например:

```text
{
    "function": "validate_token",
    "arity": 2,
    "file": "auth/token.py"
}
```

Ключевой принцип:

> **Не стоит заставлять нейронную сеть приближённо хранить информацию, которую детерминированная программа способна сохранить точно.**

Для поддерживаемых языков AST или инструменты компилятора могут предоставлять детерминированный источник символических фактов.

Однако сама символическая память также может сжиматься или отбираться при ограниченном бюджете.

---

# 4. Поведенческая память

Поведенческая информация находится между семантическим и структурным представлениями.

Например:

```text
условие
    ↓
ветвление
    ↓
побочный эффект
    ↓
исключение / возвращаемое значение
```

Одним из возможных расширений может стать явное моделирование control flow или поведенческих представлений.

Однако изначально не предполагается, что такой компонент обязательно необходим.

Исследование должно определить, достаточно ли семантической и структурной памяти для сохранения поведенческой информации.

---

# Почему не использовать один энкодер?

Монолитная архитектура выглядит так:

```text
Репозиторий
    │
    ▼
Энкодер
    │
    ▼
128 латентных единиц
    │
    ▼
LLM
```

Одна и та же латентная ёмкость должна одновременно кодировать:

```text
смысл
структуру
идентификаторы
литералы
отношения
поведение
```

В предлагаемой архитектуре репозиторий рассматривается как набор разных типов информации:

```text
Репозиторий
    │
    ├──► Семантическая память
    │
    ├──► Структурная память
    │
    └──► Символическая память
```

Исследовательский вопрос заключается в том, даёт ли такое разделение лучшую информационную эффективность.

---

# Адаптивный информационный бюджет

Самым важным компонентом предлагаемой системы является **адаптивный информационный бюджет**.

Предположим, общий бюджет памяти:

```text
B = 128 единиц
```

Обычная система может всегда использовать:

```text
Семантика       64
Структура       32
Символы         32
```

независимо от вопроса.

Предлагаемая система позволяет изменять распределение.

Например:

```text
Вопрос A

Семантика       80
Структура       32
Символы         16
```

и:

```text
Вопрос B

Семантика       24
Структура       88
Символы         16
```

Общая сумма остаётся:

```text
80 + 32 + 16 = 128

24 + 88 + 16 = 128
```

Важно именно следующее ограничение:

> **Общий информационный бюджет остаётся фиксированным.**

Меняется только его распределение.

---

# Маршрутизация с учётом вопроса

Маршрутизатор получает вопрос и определяет, какие компоненты памяти, вероятно, будут наиболее полезны.

Концептуально:

```text
                 Вопрос
                    │
                    ▼
              Энкодер вопроса
                    │
                    ▼
            Маршрутизатор
                    │
       ┌────────────┼────────────┐
       ▼            ▼            ▼
   Семантика    Структура     Символы
    бюджет       бюджет       бюджет
```

Маршрутизатор не обязан выбирать только одну память.

Он потенциально должен распределять непрерывный бюджет между несколькими типами памяти.

Например:

```text
B = 128

Семантика:      72
Структура:      40
Символы:        16
```

Конкретный механизм маршрутизации является открытым исследовательским вопросом.

---

# Постепенное раскрытие информации

Дополнительное направление — сделать информационный бюджет динамическим во времени.

Вместо немедленной передачи всей памяти:

```text
128 единиц
```

получатель сначала может получить:

```text
16 единиц
```

Если ответа недостаточно:

```text
16 → 32 → 64 → 128
```

Концептуально:

```text
Вопрос
   │
   ▼
Малая память
   │
   ▼
Получатель
   │
   ├── достаточно ──► Ответ
   │
   └── недостаточно
           │
           ▼
       Больше памяти
           │
           ▼
        Получатель
```

Это вводит вторую задачу оптимизации:

> **Сколько информации действительно необходимо модели для ответа на конкретный вопрос?**

В перспективе это может уменьшить среднее потребление информации, даже если максимальный бюджет остаётся большим.

---

# Латентная память

Непрерывные латентные представления остаются важным компонентом проекта.

Семантический энкодер может выдавать:

```text
z₁ z₂ z₃ ... zₖ
```

где:

```text
k << количество исходных токенов
```

Латентное представление выступает в роли обучаемого канала передачи информации.

Однако проект принципиально не предполагает, что вся информация должна проходить через этот канал.

Вместо этого:

```text
Семантические знания
        ↓
Латентное представление

Структурные знания
        ↓
Графовое представление

Точные символические знания
        ↓
Символическое представление
```

Это главное концептуальное отличие от монолитного латентного сжатия.

---

# Информационный бюджет как общая единица сравнения

Одной из главных экспериментальных проблем является честное сравнение различных типов памяти.

Граф, латентный вектор и набор точных символических фактов не имеют естественной общей единицы размера.

Поэтому проект требует явного определения **информационного бюджета**.

Возможные измерения:

- количество сериализованных токенов;
- байты;
- количество латентных векторов;
- количество узлов/рёбер графа;
- количество символических фактов;
- стоимость входных данных для модели;
- обучаемые коммуникационные единицы.

Точное определение бюджета само по себе является важным методологическим решением.

Финальный benchmark должен сообщать несколько ресурсных показателей, а не опираться на одну произвольную единицу.

---

# Направления оценки

Проект не должен оцениваться по одной accuracy.

Мы хотим измерять как минимум четыре измерения.

## 1. Качество выполнения задач

Может ли модель-получатель правильно отвечать на вопросы?

Возможные категории:

```text
Семантические
Структурные
Архитектурные
Поведенческие
Реляционные
Идентификаторы
Литералы
```

---

## 2. Информационная эффективность

Какое качество получается на единицу информации?

Простая концептуальная метрика:

```text
Информационная эффективность =
Качество задачи / Информационный бюджет
```

Точная метрика будет уточнена после построения надёжной методологии оценки.

---

## 3. Эффективность адаптивного распределения

Распределяет ли маршрутизатор больше бюджета именно тому типу памяти, который действительно необходим задаче?

Например:

```text
Тип вопроса        Полезная память

Семантика          Семантическая
Граф вызовов       Структурная
Точный идентификатор Символическая
```

Это можно оценивать с помощью контролируемых синтетических и реальных задач.

---

## 4. Вычислительная эффективность

Измеряются:

- входные токены;
- размер памяти;
- latency;
- throughput;
- GPU memory;
- стоимость энкодера;
- стоимость модели-получателя;
- общая стоимость inference.

Проект должен различать **информационную эффективность** и **реальную вычислительную эффективность**.

Метод может быть информационно эффективным, но вычислительно дорогим.

# Baseline'ы

Проект требует сильных baseline'ов.

## Baseline 1 — Полный контекст

Получатель напрямую получает релевантный исходный код.

```text
Код ──► LLM
```

Это предоставляет ориентир для качества при наличии полного текстового контекста.

---

# Baseline 2 — Стандартный Retrieval

Обычный pipeline поиска по репозиторию:

```text
Репозиторий
    │
    ▼
Retriever
    │
    ▼
Релевантный код
    │
    ▼
LLM
```

Возможны lexical, embedding-based или hybrid retrieval-стратегии.

---

# Baseline 3 — Сжатие контекста

Использование существующего метода сжатия кода/контекста.

```text
Репозиторий
    │
    ▼
Компрессор
    │
    ▼
Сжатый текст
    │
    ▼
LLM
```

Это позволяет проверить, лучше ли предлагаемое представление, чем простое удаление или сжатие текстовых токенов.

---

# Baseline 4 — Монолитная латентная память

Один энкодер создаёт единое латентное представление:

```text
Репозиторий
    │
    ▼
Единый энкодер
    │
    ▼
K латентных единиц
    │
    ▼
LLM
```

Это наиболее важный архитектурный baseline.

---

# Baseline 5 — Статическая гибридная память

Несколько типов памяти используются, но с фиксированным распределением:

```text
Семантика       64
Структура       32
Символы         32
```

Это позволяет отдельно измерить вклад адаптивной маршрутизации.

---

# Baseline 6 — Адаптивная гетерогенная память

Предлагаемый подход:

```text
Семантика
Структура
Символы
    │
    ▼
Адаптивный маршрутизатор
    │
    ▼
Фиксированный общий бюджет
    │
    ▼
Получатель
```

Главное сравнение:

> **Превосходит ли адаптивное распределение статическое при одинаковом общем информационном бюджете?**

---

# Основная экспериментальная матрица

Основное сравнение должно включать:

```text
A. Полный контекст

B. Retrieval

C. Сжатие текста

D. Монолитная латентная память

E. Статическая гибридная память

F. Адаптивная гибридная память
```

при контролируемых информационных бюджетах.

Например:

```text
              Низкий бюджет   Средний бюджет   Высокий бюджет

Полный контекст      -               -               ✓
Retrieval            ✓               ✓               ✓
Сжатие               ✓               ✓               ✓
Latent               ✓               ✓               ✓
Статическая Hybrid   ✓               ✓               ✓
Адаптивная Hybrid    ✓               ✓               ✓
```

Конкретные бюджеты будут определены после создания benchmark'а.

# Контрфактуальная оценка

Одной из главных проблем латентной коммуникации является то, что получатель может выдать правдоподобный ответ, не используя реально закодированную информацию.

Например:

```text
Код A:
MAX_RETRIES = 3

Код B:
MAX_RETRIES = 10
```

Изменяется только один факт.

Система создаёт:

```text
Память A
Память B
```

и мы измеряем:

- расстояние между латентными представлениями;
- ответ получателя;
- вероятность ответа;
- изменения соответствующих признаков.

Если ответ остаётся одинаковым, несмотря на изменение исходного факта, система памяти, возможно, не смогла сохранить эту информацию.

Контрфактуальные тесты поэтому предоставляют более сильное свидетельство, чем обычная accuracy.

---

# Тестирование влияния prior'ов получателя

Предположим, получатель отвечает:

> `Аутентификация реализована через validate_token().`

Есть как минимум два возможных объяснения.

### Настоящая передача информации

Энкодер передал достаточно информации, чтобы определить функцию.

### Prior получателя

Получатель сгенерировал правдоподобный ответ на основе закономерностей, уже присутствующих в его pretrained knowledge.

Поэтому проект должен включать контролируемые тесты, где:

- идентификаторы рандомизируются;
- имена функций становятся необычными;
- repository-specific константы изменяются;
- семантически эквивалентные реализации используют разные символы.

Это помогает определить, действительно ли получатель использует память репозитория.

---

# Перенос между разными моделями-получателями

Ещё один важный эксперимент — проверить, привязана ли память к конкретному получателю.

```text
                  Энкодер
                     │
                     ▼
              Общая память
                /     |      \
               /      |       \
              ▼       ▼        ▼
          Модель A  Модель B  Модель C
```

Энкодер может обучаться с одним получателем, а затем память проверяется с другим.

Вопросы:

- Переносится ли семантическая память?
- Переносится ли структурная память?
- Переносится ли символическая память?
- Какие представления зависят от конкретного получателя?
- Обобщается ли адаптивная маршрутизация?

Если память успешно переносится между моделями-получателями, это может свидетельствовать о том, что она содержит переиспользуемую информацию, а не просто кодирует частный интерфейс между двумя моделями.

---

# Интервенции над латентным пространством

Если это окажется практически реализуемым, проект может исследовать причинные связи между латентными признаками и выходами модели.

Концептуально:

```text
Исходная память
      │
      ▼
Получатель
      │
      ▼
Ответ

        vs.

Изменённая память
      │
      ▼
Получатель
      │
      ▼
Ответ изменился?
```

Если контролируемые изменения компонента памяти систематически влияют на соответствующий результат задачи, это предоставляет более сильное свидетельство того, что представление действительно содержит информацию, необходимую для задачи.

Это следует рассматривать как продвинутое направление исследования, а не как обязательное требование для первого прототипа.

Ablation крайне важен.

Возможные эксперименты:

### Удалить семантическую память

```text
Структура + Символы
```

### Удалить структурную память

```text
Семантика + Символы
```

### Удалить символическую память

```text
Семантика + Структура
```

### Отключить адаптивную маршрутизацию

```text
Статическое распределение
```

```text

```

### Заменить латентную семантическую память

```text

```

### Удалить зависимость от вопроса

```text
Одинаковое распределение памяти
для каждого вопроса
```

Эти эксперименты позволяют определить, откуда именно берётся улучшение производительности.

# Ожидаемые failure modes

Неудача является полноценной частью исследования.

Возможные результаты:

### Семантический коллапс

Семантическая память сохраняет только общие концепции.

### Структурный коллапс

Модель знает отдельные компоненты, но теряет связи между ними.

### Потеря символов

Точные идентификаторы и литералы исчезают.

### Коллапс маршрутизатора

Адаптивный маршрутизатор учится отдавать почти весь бюджет одному типу памяти.

### Неправильное распределение бюджета

Маршрутизатор выделяет информацию представлению, которое не является полезным для текущего вопроса.

### Доминирование prior'ов получателя

Получатель отвечает на основе pretrained knowledge, а не памяти репозитория.

### Запутанность представлений

Разные типы информации невозможно эффективно разделить.

### Несовместимость между получателями

Память работает только с той моделью, с которой она обучалась.

### Накладные расходы progressive disclosure

Стоимость дополнительных запросов информации превышает получаемую экономию.

### Превосходство retrieval

Обычный retrieval остаётся эффективнее при том же вычислительном бюджете.

Любой из этих результатов может оказаться научно полезным.

# Чем этот проект отличается

Проект не строится на предположении:

> «Латентные токены лучше текста».

Вместо этого он исследует:

> **«Имеет ли тип представления значение, когда информационный бюджет ограничен?»**

Поэтому основное сравнение:

```text
Монолитная память
       │
       ▼
Одно представление
       │
       ▼
Один bottleneck


            VS


Гетерогенная память
       │
 ┌─────┼─────┐
 ▼     ▼     ▼
Сем.  Стр.  Сим.
 │     │     │
 └─────┼─────┘
       ▼
Адаптивное распределение
       │
       ▼
Одинаковый общий бюджет
```

Это превращает проект в проверяемую исследовательскую гипотезу, а не просто ещё одну архитектуру.

---

# Чем этот проект НЕ является

Проект не предназначен для создания:

- очередного ChatGPT-клона;
- очередного универсального coding assistant;
- простой RAG-обёртки;
- очередного туториала по vector database;
- проекта по prompt engineering;
- очередного generic context compressor;
- утверждения, что латентные представления автоматически заменяют retrieval;
- утверждения, что детерминированная символическая память всегда лучше;
- утверждения, что гетерогенная память обязательно превзойдёт существующие методы.

Архитектура является гипотезой.

Эксперименты должны определить, работает ли она.

# Потенциальные применения

Если подход окажется полезным, возможны следующие применения.

## Постоянная память репозитория

Кодовую базу можно закодировать в компактную гетерогенную память и повторно использовать между сессиями.

## Долгоживущие coding agents

Агенты могут поддерживать постоянные представления больших кодовых баз, не обрабатывая весь репозиторий заново.

## Адаптивное сокращение контекста

Простые вопросы могут использовать очень маленький информационный бюджет, тогда как сложные вопросы получают дополнительную информацию.

## Коммуникация между несколькими моделями

Разные модели потенциально могут использовать одну и ту же память репозитория.

## Понимание репозитория

Память может выступать компактным представлением семантических, структурных и символических знаний.

Это потенциальные применения, а не уже доказанные возможности.

Возможные вклады:

### Вклад A — Гетерогенная память кода

Фреймворк для разделения семантических, структурных и символических знаний о репозитории.

Обучаемый механизм распределения фиксированного информационного бюджета между типами памяти.

Систематическое исследование того, какие типы знаний о коде сохраняются при различных стратегиях сжатия.

Исследование того, может ли обученная память кода использоваться разными моделями-получателями.

### Вклад G — Отрицательные результаты

Чёткая демонстрация случаев, когда гетерогенная память не работает или не даёт преимуществ.

Финальный вклад будет определён экспериментальными результатами.

# Информационная эффективность

Одна из центральных целей — выйти за рамки простой accuracy.

Предположим:

```text
Система A
90% accuracy
1000 информационных единиц

Система B
88% accuracy
128 информационных единиц
```

Система B может быть значительно эффективнее с точки зрения информации.

Поэтому проект будет исследовать метрики, связывающие:

```text
Качество задачи
        ↕
Информационный бюджет
        ↕
Вычислительная стоимость
```

Финальное определение метрики будет установлено до основного сравнения, чтобы избежать оптимизации оценки после получения результатов.

# Как выглядит успех

Успех необязательно означает:

> «Наша модель победила все baseline'ы».

Успешным результатом может быть, например:

> При одинаковом информационном бюджете гетерогенная память лучше сохраняет семантическую, структурную и символическую информацию, чем монолитное латентное сжатие.

Или:

> Адаптивное распределение обеспечивает измеримое улучшение по сравнению со статическим при одинаковом общем бюджете.

Или:

> Семантическая информация хорошо подходит для латентных представлений, тогда как точная символическая информация лучше сохраняется с помощью детерминированных представлений.

Или:

> Progressive disclosure снижает среднее потребление информации без существенного снижения качества ответов.

Или:

> Гетерогенная память в целом не даёт преимущества, но выявляет сильное и воспроизводимое разделение между типами информации.

Даже отрицательный результат может иметь научную ценность, если сравнение выполнено строго и воспроизводимо.

# Ограничения

Предлагаемый подход может иметь значительные ограничения.

Он может:

- требовать несколько энкодеров или этапов обработки;
- добавлять overhead маршрутизации;
- быть вычислительно дороже простого retrieval;
- создавать сложности при определении честного общего информационного бюджета;
- создавать несовместимые представления;
- терять информацию во время семантического сжатия;
- зависеть от архитектуры получателя;
- требовать language-specific static analysis;
- испытывать проблемы с динамическим поведением программ;
- плохо работать с неизвестными репозиториями;
- иметь худшую latency по сравнению с retrieval;
- требовать значительного количества обучающих данных.

Эти ограничения должны быть явно измерены и описаны.

Более широкий вопрос проекта:

> **Можно ли эффективнее хранить структурированные знания, если разные типы информации представлять в соответствии с их внутренними свойствами, а не заставлять всё проходить через единое обучаемое представление?**

Код является особенно подходящей областью для исследования этого вопроса, поскольку содержит:

- точные символы;
- иерархическую структуру;
- семантические отношения;
- графы зависимостей;
- исполняемое поведение;
- точные литералы;
- дальние зависимости;
- как высокоуровневую, так и низкоуровневую информацию.

Таким образом, проект находится на пересечении:

```text
Code Intelligence
       +
Representation Learning
       +
Information Bottlenecks
       +
Learned Memory
       +
Neural Communication
```

Долгосрочная цель заключается не просто в создании меньшего контекста.

Цель — понять, **как разные виды знаний следует представлять и передавать при ограниченном количестве доступной информации**.

# Исследовательская философия

Проект следует нескольким принципам.

## 1. Доказательства важнее интуиции

Интересные идеи должны проверяться экспериментально.

## 2. Baseline'ы важнее изолированных результатов

Одной цифры без meaningful comparison недостаточно.

## 3. Сравнение при одинаковом бюджете

Методы следует сравнивать при контролируемых информационных и вычислительных ограничениях, когда это возможно.

## 4. Отрицательные результаты имеют ценность

Неудачная гипотеза может раскрыть важные свойства представления и памяти для кода.

## 5. Воспроизводимость важнее эффектности

Все важные результаты должны быть воспроизводимыми.

## 6. Детерминированные инструменты там, где это уместно

Нейронная сеть не должна приближённо хранить информацию, которую статический анализ программы способен сохранить точно, если на это нет исследовательской причины.

## 7. Понимание важнее скорости реализации

Проект одновременно является исследовательским и образовательным процессом.

## 8. Никакого заранее определённого вывода

Мы не знаем, превзойдёт ли адаптивная гетерогенная память существующие методы.

Вывод должен определяться экспериментами.

# Финальный исследовательский вопрос

В конечном счёте проект задаёт вопрос:

> **Когда количество информации, доступной языковой модели, строго ограничено, лучше ли сжимать всё в одно обучаемое представление — или же представлять семантические, структурные и символические знания по-разному и динамически распределять между ними доступный информационный бюджет?**

Цель проекта — не просто создать очередной компрессор кода.

Цель — исследовать, может ли **гетерогенная адаптивная память сделать рассуждение о коде при ограниченном объёме информации более эффективным, надёжным и интерпретируемым, чем монолитное сжатие**.

И независимо от результата проект должен дать воспроизводимый ответ на этот вопрос.
